AI 진로 두 갈래

진로 탐색 노트2026년 10월 기준

AI로 서비스를 기획하는 길과 AI로 웹을 만드는 길

두 진로 모두 AI를 매일 쓰는 직업입니다. 기획은 무엇을 만들지 정하고 결과의 품질을 판단합니다. 개발은 그것을 실제로 동작하는 웹 서비스로 만듭니다. 이 페이지는 두 길이 하는 일, 필요한 역량, 도구, 준비 방법을 한곳에 모았습니다.

AI 서비스 기획

사용자의 문제를 찾고, AI로 풀 방법을 설계하고, AI 응답이 쓸 만한지 평가해서 개선합니다.

Shared ground

두 길이 같이 쓰는 기본기

  • AI 결과를 검증하는 습관

    AI는 그럴듯한 오답도 냅니다. 기획자는 응답의 정확성과 맥락을, 개발자는 코드의 동작과 보안을 직접 확인합니다.

  • 문제를 구체적으로 설명하는 글쓰기

    원하는 것을 정확히 적을수록 AI의 결과가 좋아집니다. 기획서와 프롬프트는 같은 글쓰기 능력에서 나옵니다.

  • 계속 바꿔 가는 학습

    도구가 빠르게 바뀌어서 한 번 익힌 사용법이 오래가지 않습니다. 새 도구를 실제 작업에 넣어 보는 습관이 필요합니다.[2]

Path A

AI 서비스 기획

서비스기획자, 프로덕트 매니저(PM), AI 서비스 기획자 같은 이름으로 채용됩니다. 고객의 요구를 분석하고 AI 기술로 사용자 경험을 높이는 방법을 찾아 팀과 함께 구현하는 일입니다.[3]

하는 일
  • 사용자가 겪는 문제를 찾고, AI로 푸는 것이 맞는지 판단합니다. 규칙 기반 기능이 더 나은 경우도 있습니다.
  • 요구사항을 PRD(제품 요구사항 문서)와 와이어프레임으로 정리해 개발팀과 디자인팀에 전달합니다.
  • AI 서비스의 테스트 시나리오와 테스트 케이스를 관리하고, 실제 사용자처럼 써 봅니다.[1]
  • AI 응답이 자연스러운지, 정확한지, 알맞은 시점에 나오는지 평가하고 개선점을 정리합니다.[1]
  • 사용률과 만족도 같은 지표로 성과를 확인하고, 개인정보와 윤리 이슈를 점검합니다.[9]
필요 역량

기술 이해

  • AI와 LLM이 어떻게 동작하고 어디에서 틀리는지 아는 것. 모델을 직접 만들 필요는 없습니다.[2]
  • 데이터를 읽고 의미를 뽑는 능력. 스프레드시트와 SQL 기초면 시작할 수 있습니다.

설계와 소통

  • AI와 사용자 경험(UX)을 함께 설계하는 능력.[2]
  • 기획 의도를 글로 분명하게 쓰는 문서화.
  • AI 개발자, 데이터 담당자, 디자이너와 협업하며 기술과 사업 목표를 연결하는 소통.[2]
자주 쓰는 도구
  • Claude, ChatGPT, Gemini아이디어 정리, 문서 초안, 시나리오 생성, 프롬프트 실험
  • Figma화면 흐름과 와이어프레임
  • Notion, 구글 문서PRD와 회의 기록
  • 스프레드시트, SQL평가표 작성과 로그 분석
  • GA4 같은 분석 도구사용자 행동 확인
포트폴리오 아이디어
  • 자주 쓰는 앱 하나를 골라 AI 기능을 붙이는 기획서. 문제 정의, PRD, 화면 흐름, 성공 지표를 담습니다.
  • AI 응답 평가표. 테스트 케이스, 점수 기준, 발견한 문제, 개선안을 담습니다.
  • AI 도구로 만든 클릭 가능한 프로토타입과 사용자 테스트 결과.
채용에서 보는 것

AI 서비스 기획 인턴 공고를 분석한 글에서는 화려한 개발 실력보다 꼼꼼한 반복 검증, 문제의 원인을 따져 보는 습관, 사용자 관점의 판단을 중요하게 봅니다.[1] 현업 팀장이 쓴 글에는 AI를 써 봤다는 경험보다 업무에 어떻게 녹여 쓰는지를 면접에서 묻는다는 내용이 있습니다.[4]

주의할 점

AI가 화면 초안과 문서까지 만들어 주기 때문에, 문서만 쓰는 신입은 대체되기 쉽다는 걱정이 취업 커뮤니티에 올라옵니다.[5] AI 결과를 그대로 쓰지 않고 근거를 들어 고치는 힘, 한 업계를 깊이 아는 이해, 지표로 검증하는 습관이 차별점이 될 수 있습니다.

Path B

AI 툴 웹개발

프론트엔드, 풀스택, 웹 개발자로 일합니다. AI 도구가 개발 속도를 높여 주지만 코드의 정확성과 책임은 개발자에게 남습니다.

하는 일
  • HTML, CSS, JavaScript(TypeScript)와 React, Next.js 같은 프레임워크로 화면과 기능을 만듭니다.
  • 서버, 데이터베이스, 로그인을 연결합니다. Supabase 같은 서비스로 백엔드를 빠르게 구성하기도 합니다.
  • AI 코딩 도구에 작업을 설명하고, 나온 코드를 읽고 고칩니다.
  • 버그 원인 찾기, 리팩터링, 테스트 코드 작성을 AI와 함께 진행합니다.
  • 서비스에 AI 기능을 붙입니다. AI 모델을 서버와 API로 연결해 결과를 화면에 보여 주는 방식입니다.[9]
  • 서비스를 배포하고 오류를 확인합니다.
필요 역량

기본기

  • HTML, CSS, JavaScript와 반응형 화면 구성.
  • Git과 GitHub로 작업 기록 남기기.
  • 코드를 읽고 틀린 곳을 찾는 능력. AI가 준 결과를 판단하려면 꼭 필요합니다.

서비스 이해

  • 서버, 데이터베이스, API의 기초.
  • 보안 기본기. API 키 보관과 입력값 검증이 대표적입니다.
  • 테스트와 배포 과정.

AI 활용

  • 작업을 작게 나누고, 필요한 맥락을 전달하고, 결과를 검증하는 방법. 도구를 제대로 쓰지 못하면 시간만 쓰고 기술 부채가 늘 수 있다는 지적이 있습니다.[8]
자주 비교되는 도구
  • CursorVS Code를 기반으로 만든 AI 에디터. 코드를 보면서 바로 제안을 받아 적용하는 일상 코딩에 맞습니다.[6][7]
  • Claude Code터미널에서 프로젝트 단위 작업을 맡기는 에이전트. 여러 파일에 걸친 수정과 분석에 쓰입니다.[6]
  • GitHub Copilot쓰던 편집기에 붙이는 확장. 회사 보안 정책과 GitHub 연동이 중요한 환경에서 많이 씁니다.[6]
  • Windsurf무료 티어로 에이전트 기능을 먼저 써 볼 수 있습니다.[7]

에디터형 도구와 터미널 에이전트를 함께 쓰는 개발자가 많다는 비교 글이 있습니다.[7] 요금제와 기능은 자주 바뀌므로 각 공식 사이트에서 확인하세요.

AI와 일하는 한 사이클
  1. 만들 기능을 작게 나눠 글로 설명합니다.
  2. AI가 코드를 생성합니다.
  3. 코드를 읽고 직접 실행해 확인합니다.
  4. 테스트를 돌리고 틀린 부분을 고칩니다.
  5. 커밋하고 배포합니다.
포트폴리오 아이디어
  • 배포 링크가 있는 웹 서비스 2~3개. 그중 하나는 로그인과 데이터베이스를 포함합니다.
  • LLM API를 붙인 기능 하나. 요약이나 추천이 시작하기 좋습니다.
  • README에 AI에게 맡긴 부분과 직접 설계하고 검증한 부분을 나눠 적고, 커밋 기록을 꾸준히 남깁니다.
주의할 점

AI가 만든 코드를 이해하지 못한 채 쓰면 오류를 고치지 못하고, 보안 문제를 놓치기 쉽고, 기술 부채만 쌓일 수 있습니다.[8] 코드를 읽는 기본기를 먼저 쌓은 뒤 AI 도구로 속도를 올리는 순서가 안전합니다.

이런 일이 즐겁다면 기획

일반적인 경향이며 정답은 아닙니다.

  • 사람들이 불편해하는 지점을 찾아내는 일
  • 생각을 문서와 도표로 정리하는 일
  • 숫자로 결과를 확인하고 다음 개선을 정하는 일
  • 여러 직군의 의견을 조율하는 일

이런 일이 즐겁다면 개발

일반적인 경향이며 정답은 아닙니다.

  • 직접 만든 것이 화면에서 동작하는 순간
  • 오류의 원인을 끝까지 추적하는 일
  • 새 도구와 기술을 파고들어 써 보는 일
  • 혼자 집중해서 문제를 푸는 일

두 길이 만나는 곳

AI 서비스를 만드는 팀에서는 기획자와 개발자가 같은 제품을 번갈아 다룹니다. 한 번의 개선은 보통 이런 순서로 돌아갑니다.

  1. 1 기획

    문제와 요구사항 정리

    PRD와 화면 흐름을 만들고 성공 지표를 정합니다.

  2. 2 개발

    AI 도구로 구현

    기능을 만들고 코드를 검토해 테스트할 수 있는 버전을 냅니다.

  3. 3 기획

    시나리오로 품질 평가

    실제 사용자처럼 써 보고 AI 응답을 평가표로 점수화합니다.

  4. 4 함께

    개선, 배포, 지표 확인

    발견한 문제를 고치고 배포한 뒤 지표를 같이 봅니다.

AI 기획자는 기술 이해와 커뮤니케이션이 함께 강조되는 직무로 설명됩니다.[3] 그래서 기획을 하면서 AI 도구로 간단한 프로토타입을 직접 만들어 보는 길도 선택지가 됩니다. 반대로 개발자가 기획 문서를 읽고 사용자 관점에서 판단할 수 있으면 팀에서 더 쓸모가 큽니다. 두 길 중 하나를 정한 뒤에도 상대 직군의 기초를 조금씩 익혀 두면 좋습니다.
